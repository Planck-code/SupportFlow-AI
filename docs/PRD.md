# SupportFlow AI 产品需求文档

> 状态：M1 服务骨架已实现；本文中的账号、工单和后续业务功能仍为开发规划。
> 更新日期：2026-11-02。
> 技术设计见 [ARCHITECTURE.md](ARCHITECTURE.md)，任务与验收见 [ROADMAP.md](ROADMAP.md)。

## 1. 项目定位与目标

SupportFlow AI 是一个基于 Go 的智能客服工单管理平台，面向 Go 后端实习求职展示，同时用于学习完整后端工程实践。普通用户提交问题，客服负责沟通与解决，管理员负责分配和转派；后续引入 AI 分类、摘要和回复建议。

项目优先展示以下能力：

- Go 工程组织、Gin HTTP 接口、参数校验与错误处理。
- JWT 认证、角色授权和业务数据归属检查。
- MySQL 表设计、索引、事务及并发控制。
- 自动化测试、Docker Compose 与可复现运行。
- 在可靠业务流程上接入大模型，并处理模型超时和异常输出。

不以功能数量或 AI 自动化程度作为成功指标。阶段一的成功标准是能够演示“用户提交 → 客服认领或管理员分配 → 双方回复 → 客服解决 → 用户关闭”，并解释权限和一致性如何得到保证。

## 2. 用户角色与权限

系统只有三个互斥角色，一个账号对应一个角色。

| 角色 | 主要权限 | 数据范围 |
| --- | --- | --- |
| 普通用户 `user` | 注册、登录、创建工单、回复、重开、关闭 | 仅自己的工单、消息和事件 |
| 客服 `agent` | 登录、认领、回复、调整优先级、标记解决 | 自己负责的工单，以及未分配队列摘要 |
| 管理员 `admin` | 登录、分配、转派、调整优先级、关闭、查看全部工单 | 全部工单、消息和事件 |

权限约束：

- 公开注册只能创建 `user`，客户端不能提交角色实现提权。
- 客服和管理员通过初始化命令创建，MVP 不开发人员管理后台或角色修改接口。
- 管理员不发送客服回复，也不兼任客服；分配目标只能是 `agent`。
- 客服不能查看其他客服负责工单的详情，也不能主动转派。
- 未分配队列仅返回编号、标题、分类、优先级和创建时间，不返回正文、消息或用户资料。
- 客服认领前不能读取工单详情、消息、事件；认领成功后才获得访问权限。
- 转派提交后，原客服的后续访问立即按新归属校验。
- 普通用户不能访问未分配队列，管理员通过全部工单列表筛选未分配工单。

## 3. 阶段一：MVP 功能范围

### 3.1 身份与账号

- 邮箱、密码注册；邮箱规范化后唯一。
- 邮箱、密码登录，签发短期 JWT。
- 获取当前登录用户信息。
- 命令行初始化管理员和客服；管理员查询客服列表用于分配。
- 不包含邮箱验证、找回密码、刷新令牌或服务端注销。

### 3.2 工单提交与查询

- 普通用户提交标题、描述和分类，创建时状态为 `open`、负责人为空、优先级为 `normal`。
- 分类固定为 `general/account/billing/technical`，默认 `general`，不建设分类管理功能。
- 普通用户列出自己的工单；客服列出自己负责的工单；管理员列出全部工单。
- 列表支持分页、状态和分类筛选；管理员可以按负责人筛选。
- 客服通过单独的未分配队列寻找待认领工单。
- 详情、消息、操作记录均校验数据访问权限。

### 3.3 认领、分配与沟通

- 客服认领未分配工单，管理员也可主动分配。
- 管理员可在处理中转派给另一名客服。
- 工单所属用户和当前负责客服可新增公开文字回复。
- 回复不可修改、不可删除；不包含内部备注、附件或富文本。
- 当前负责客服或管理员可以在处理中调整优先级，取值仅为 `normal/high`。

### 3.4 状态流转

```text
用户创建
   ↓
open（未分配）
   ↓ 客服认领 / 管理员首次分配
in_progress（处理中）
   ↓ 当前负责客服标记解决
resolved（已解决）
   ├─ 所属用户重开 → in_progress
   └─ 所属用户 / 管理员关闭 → closed（终态）
```

| 动作 | 执行人 | 前置条件 | 结果 |
| --- | --- | --- | --- |
| 创建 | 普通用户 | 输入有效 | `open`，无负责人 |
| 认领 | 客服 | `open` 且无负责人 | `in_progress`，负责人为当前客服 |
| 首次分配 | 管理员 | `open` 且无负责人；目标为客服 | `in_progress`，设置负责人 |
| 转派 | 管理员 | `in_progress`；目标为另一名客服 | 保持状态，更新负责人 |
| 调整优先级 | 当前负责客服或管理员 | `in_progress` | 更新优先级 |
| 回复 | 所属用户或当前负责客服 | `open` 或 `in_progress` | 新增消息，状态不变 |
| 解决 | 当前负责客服 | `in_progress` | `resolved`，保留负责人 |
| 重开 | 所属用户 | `resolved` | `in_progress`，保留负责人 |
| 关闭 | 所属用户或管理员 | `resolved` | `closed` |

`open` 没有负责人，因此此时实际只有所属用户能回复。已解决工单必须先重开才能继续回复。关闭后不能重开、回复、转派或调整优先级。

不提供通用状态修改接口，不支持直接关闭未解决工单、取消工单、编辑或删除工单。重复认领、重复关闭等状态动作返回冲突；把负责人或优先级设置为当前值视为无变化，返回成功且不新增事件。

### 3.5 操作记录

创建、回复、认领、分配、转派、优先级变化、解决、重开和关闭均记录操作者及时间。分配、优先级和状态事件保存必要的前后值；回复事件只关联消息 ID，不重复存储消息正文。

业务更新和事件写入作为同一个事务提交。事件不能通过公开接口修改或删除。

### 3.6 MVP 验收标准

- 普通用户与客服完成一次完整闭环，管理员完成一次分配和转派。
- 用户不能读取或操作他人工单；客服不能读取非负责工单详情。
- 两名客服并发认领同一工单，恰好一人成功，另一人收到 `409`。
- 非法状态操作被拒绝；事件写入失败时业务变化回滚。
- 接口可通过请求示例独立验收，不依赖前端。
- 他人能够按 README 从空数据库启动并重现演示流程。

## 4. 阶段二：AI 辅助与演示前端

AI 由当前负责客服主动触发，一次生成建议分类、摘要和回复建议。结果仅供人工参考，不自动修改工单分类，也不自动发送消息。

- 模型超时、上游错误或非法输出不影响工单的提交、回复和状态处理。
- 保存调用记录、模型、输入快照标识和结果，展示输入截断及结果是否过时。
- 管理员可读取结果，普通用户不能访问 AI 分析记录；原客服转派后不能读取该工单的分析记录。
- 客服可复制并修改回复建议，再通过普通回复接口发送，不建设独立自动回复链路。
- Vue 3 + Element Plus 只实现登录、用户工单、客服队列与详情、管理员分配等演示页面。

阶段门槛：至少验证一次真实模型调用；自动化测试使用假客户端，不依赖模型额度；AI 失败时人工流程仍可运行。

## 5. 阶段三：后端工程增强

- Redis 用于登录限流，暂不引入工单缓存。
- 增加管理员基础工单计数和查询性能分析。
- 完善优雅停机、超时、日志审查和 CI。
- 验证空库迁移与版本升级迁移，整理架构说明和面试演示材料。

阶段门槛：有真实测试与测量结果，能够说明限流、索引和工程措施解决的具体问题，不编造性能数字。

## 6. 暂缓功能与边界

| 暂缓功能 | 原因 |
| --- | --- |
| Redis 工单缓存 | 先验证数据库查询，避免提前处理缓存一致性 |
| AI 自动回复、自动分配 | 需要更完整的评估、人工控制和失败处理 |
| RAG、向量数据库、多 Agent | 先验证单次模型调用的实际价值 |
| 附件、邮件、短信、WebSocket | MVP 闭环不依赖这些存储或异步链路 |
| 多租户、部门、动态权限配置 | 三角色足以展示基本授权能力 |
| SLA、满意度、复杂报表 | 属于后续产品能力，不影响当前展示目标 |
| 微服务、消息队列、Kubernetes | 当前规模与学习目标不需要 |

所有新增需求先归入独立任务并定义验收条件，不顺带加入当前开发。
